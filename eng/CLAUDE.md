# ALTGEO — брифинг проекта для Claude Code

> В репозитории oneone это инженерная часть, смонтированная в основное
> приложение по адресу `/eng` (см. `app/main.py`). Вход только для
> администратора ALTGEO (`require_admin` в `eng/web.py`), общий пароль
> `/login` и клиентский раздел `/monitor` убраны: клиентов обслуживает
> кабинет основного сайта. Приём данных от устройств делает основной сайт и
> копирует их сюда через `eng/feed.py`. Разделы про Docker ниже описывают
> старое развёртывание; сейчас сайт живёт на REG.RU (см. README.md в корне).

Прочитай это целиком перед тем, как что-либо менять на сервере. Здесь —
архитектура, принятые решения и, что важнее всего, реальные грабли, на
которые уже наступали. Повторять их не нужно.

## Что это

ALTGEO — платформа гибридного позиционирования (GPS + WiFi + BLE) для
транспортного мониторинга и логистики. Flask/SQLite сервер + два типа
аппаратных трекеров на ESP32 (прошивки на Arduino/C++).

**Цель первого этапа: стабильная работа с 50 устройствами.**
**Актуальный статус, задачи и открытые вопросы — смотри `/roadmap` на
самом сайте (раздел в инженерной панели), не здесь. Этот файл — про
архитектуру и грабли, а не про то, что сейчас в работе.**

## Постоянные принципы проекта (не подлежат пересмотру)

1. **Токен-модель оплаты**: клиент платит только за фактически
   потреблённые ресурсы (мощности + работа команды), без фиксированных
   плат и подписок.
2. **Данные всегда работают на всю платформу**: WiFi/BLE-данные от любого
   устройства попадают в общий пул (`networks`, `stable_networks`) и
   улучшают точность для всех клиентов сразу. Никогда не изолировать
   данные по клиенту.
3. **Прошивка — всегда предельно просто, навсегда**: подключил -> выбрал
   устройство -> нажал «Прошить» -> готово. Клиент **никогда** не выбирает
   файлы со своего компьютера. Уже реализовано (`/tracker/flash`, Web
   Serial API) — не ломать при будущих изменениях.

## Три + один режима сайта

1. **Инженерный** (`/login` -> `/map` и весь набор внутренних инструментов:
   Map, Reports, Cleanup, Algorithm Lab, Admin, Devices, Users, Tracker,
   Roadmap, Upload logs). Без саморегистрации — единый пароль
   (`WIFIGPS_PASSWORD`), раздаётся вручную.
2. **Клиентский** (`/monitor/*`) — самостоятельная регистрация по email,
   привязка устройства по IMEI/Chip ID, просмотр трека.
3. **Загрузчик ПО** (`/tracker`, `/tracker/flash`) — два типа устройств,
   прошивка прямо из браузера (esptool-js), без выбора файлов клиентом.
   Загружает/обновляет прошивки только инженер.
4. **Roadmap** (`/roadmap`) — общая доска задач/заметок/предложений,
   правит и Иван, и Claude.

## Устройства

| Тип (`device_types.key`) | Плата | Идентификация | Связь | SD-карта |
|---|---|---|---|---|
| `devtr` | LILYGO T-Pager | Chip ID | WiFi (HTTPS) | есть |
| `altgeo-gsm` | LILYGO T-Call A7670 | IMEI (виден через BLE-рекламу `ALTGEO_IMEI_...`) | GSM, реалтайм | нет, полностью автономно |

Прошивки: `.ino` в отдельных репозиториях, собираются облачно через
GitHub Actions (`.github/workflows/build.yml` в каждом репо) — компилятора
на этой машине нет, все сборки проверялись только через CI и разбор
исходников библиотек.

## Развёртывание

- Docker Compose, одна папка на хосте: `./data` (БД + прошивки,
  bind-mount, НЕ named volume) и `./uploads`.
- `./data/wifigps.db` — вся база SQLite.
- `./backups/` — **новое**: автоматический ежедневный бэкап БД (SQLite
  backup API, безопасен при живой записи) + при каждом старте сервера,
  ротация — последние 14 штук. Ручной запуск: `python3 backup_now.py
  --data-dir ./data`, или кнопка на `/admin`.
- Переменные окружения: `WIFIGPS_SECRET_KEY`, `WIFIGPS_DATA_DIR`,
  `WIFIGPS_PASSWORD` — смотри реальные значения в `docker-compose.yml` на
  сервере, здесь намеренно не приводятся.
- HTTPS настраивает сам Иван (свой reverse proxy) — сервер сам по себе
  отдаёт только plain HTTP на 5000.

## Схема БД (основное)

`sessions`, `points`, `observations`(WiFi), `ble_observations`,
`networks`/`ble_devices` (агрегаты по всем данным), `stable_networks`/
`stable_ble_devices` (только подтверждённые в ≥2 сессиях И рядом с
реальным треком), `estimated_positions` (GPS-независимая оценка по ВСЕМ
сетям), `excluded_devices` (попутчики + далёкие от трека, с
`user_override`), `devices`/`device_types`/`device_firmwares`,
`monitor_users`, `roadmap_items`, `daily_stats`/`network_snapshot`
(история), `settings`.

Важно: `estimated_positions` использует ВСЕ известные сети (шумные
включительно). Режим Showroom на карте использует **только**
`stable_networks`/`stable_ble_devices` — это разные, намеренно разные
источники, не путать при доработках.

## Конвейер обработки (`jobs.py`, `run_processing`)

Порядок важен: очистка выбросов скорости -> обнаружение попутчиков ->
`recompute_networks`/`recompute_ble_devices` -> `detect_network_far_from_track`
(WiFi, затем BLE) -> повтор recompute -> `purge_bad_gps_points` ->
`recompute_estimated_positions` -> `compute_stable_points` (**обязательно
после** обнаружения попутчиков и far-from-track — иначе они просочатся в
стабильные, см. грабли ниже) -> снимок дня.

## Грабли, на которые уже наступали — не повторять

1. **Docker named volumes -> bind mount не переносит данные
   автоматически.** Однажды почти потеряли реальную БД при смене
   `docker-compose.yml`. Теперь `./data` — bind mount, но при ЛЮБОЙ смене
   конфигурации volumes — сначала бэкап, потом менять.
2. **Никогда не паковать тестовую/пустую БД в архив с кодом.** Был
   близкий промах: тестовая `wifigps.db` почти уехала в архив для
   продакшена. Теперь `data/*` всегда явно исключается при сборке
   архивов.
3. **Права на `./data/firmware/`**: файлы создаёт контейнер (обычно
   root), скрипты с хоста от обычного пользователя могут получить
   `PermissionError`. Фикс: `sudo chown -R $(id -u):$(id -g) ./data`.
4. **Коррелированный подзапрос в `recompute_networks`** пересканировал
   всю `observations` на каждую сеть — 50 секунд на 22 тыс. сетей.
   Переписано через оконную функцию за один проход — 0.1с. Если что-то
   в проекте снова "внезапно тормозит на масштабе" — искать именно такой
   паттерн первым делом.
5. **Отсутствие индекса на `points(status, lat, lon)`** — то же самое,
   `detect_network_far_from_track` сканировал все точки на каждую сеть.
   Индекс уже добавлен, но при добавлении новых "далеко от трека"-проверок
   проверять индексы сразу, не постфактум.
6. **`compute_stable_points` должен фильтровать `excluded_devices` И
   проверять близость к треку сам** — иначе попутчики и "загрязнённые"
   усреднения (сеть видели раз здесь, раз в другом городе — средняя точка
   нигде реальная) попадают в "стабильные" и создают лучевые артефакты на
   карте (после проверки собственных наблюдений над скриншотами — было
   именно так).
7. **Дедупликация линий трека на карте — через граф рёбер, не через
   привязку к сетке.** Привязка к общей сетке координат сама по себе не
   гарантирует дедупликацию, если разные сессии проезжают перекрёсток
   слегка по-разному — тогда всё равно получается веер пересекающихся
   отрезков. Правильно: снэппинг + рёбра между соседними ячейками
   собираются в `set()` (дедуп по построению) + отсечение рёбер длиннее
   ~300м (признак спуфинга/джаминга, не реального движения).
8. **esptool-js: передавать `Uint8Array` напрямую, никогда не через
   `String.fromCharCode()`.** Конвертация в строку и обратно ломает любой
   байт ≥128 при последующем сжатии (`compress: true` внутри `writeFlash`)
   — прошивка приходит на устройство повреждённой без единой явной
   ошибки на этом шаге.
9. **TinyGSM: макроса `TINY_GSM_MODEM_A7670` не существует** в основной
   библиotece (только в форке LilyGO). Для A7670 использовать
   `TINY_GSM_MODEM_SIM7600` — так же делает сам LilyGO в официальном
   примере ("A7670 совместим с набором AT-команд SIM7600").
10. **ESP32 + BLE + TinyGSM легко не влезает в дефолтную схему разделов**
    (1.3МБ на приложение). Использовать `PartitionScheme=no_ota` (2МБ/2МБ) —
    OTA-обновления в прошивке не используются, терять нечего.
11. **Web Serial API работает только по HTTPS** (или на `localhost`) —
    без TLS браузер молча скрывает `navigator.serial`, выглядит как "не
    та версия браузера", хотя причина другая.
12. **Проверка TLS-сертификата на ESP32 требует реально выставленных
    системных часов** — mbedTLS сверяет срок действия сертификата с
    часами устройства. Без NTP-синхронизации (после подключения к WiFi,
    до первого HTTPS-запроса) проверка сертификата падает даже с
    полностью корректным сертификатом.
13. **Jinja2: не называть ключ словаря `items`** — конфликтует со
    встроенным методом `dict.items()`, `sec.items` в шаблоне резолвится в
    сам метод, а не в значение. Использовать другое имя (`entries` и т.п.).

## Практика безопасной работы на этом сервере

- Перед любой операцией, которая может задеть `./data` (миграции, смена
  volumes, ручные правки БД) — сначала `python3 backup_now.py --data-dir
  ./data`.
- Никогда не перезаписывать `./data` содержимым из архива/скрипта без
  явного подтверждения человека.
- Скрипты-помощники уже существуют для типовых задач: `seed_firmware.py`
  (добавить/обновить прошивку в каталоге), `seed_roadmap.py` (разовое
  наполнение Roadmap), `backup_now.py` (разовый бэкап), `migrate_old_volumes.sh`
  и `diagnose_data.sh` (диагностика/перенос из старых named volumes, если
  когда-нибудь понадобится снова).
